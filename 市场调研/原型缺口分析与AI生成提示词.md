# 智能外呼原型缺口分析与 AI 生成提示词

> 用途：用于指导其他 AI 在现有 `smartcall-pro` 原型基础上继续补齐关键页面与交互。
>
> 结论依据：现有原型前端实现、市场调研目录中的 MVP/落地方案/红娘 BRD-PRD，以及 SmartCall 源码中可读取到的数据模型、流程节点、权限与知识库集成结构。
>
> 重要边界：本文只描述“原型应该展示什么”和“源码存在什么支撑”。模拟数据、README 描述、数据表或 Java 模型都不等于生产能力已经完成或通过验证。

## 一、总体差距结论

现有 `smartcall-pro` 已覆盖主要业务展示链路：

```text
运营驾驶舱
→ 外呼任务
→ 潜客中心
→ AI 通话沙盒
→ 高意向转红娘
→ 红娘跟进
→ 智能质检
→ 转化与 ROI 报表
→ 规则与 AI 引擎配置
```

因此，它并不是“页面很少的空原型”，对下周演示所需的业务故事已经具备较完整的表达能力。

但若按需求文档中的完整 MVP、运营管理要求和 SmartCall 技术能力边界衡量，当前仍属于“业务演示型业务工作台”，还不是完整的“可配置、可监控、可审计、可接入真实服务”的平台。这里不建议把所有能力都堆进一个笼统的“后台”里，而是拆成同一套产品中的两类区域：高频业务工作台和低频系统管理区。主要问题是：

1. 部分关键流程被压缩在弹窗、抽屉或模拟沙盒中，没有形成正式工作页面。
2. 潜客授权、审核、退订、黑名单、频控等合规信息展示不够系统。
3. 缺少正式的实时任务监控和全量通话记录台账。
4. 现有规则页不能替代机器人、IVR 流程和知识库管理。
5. 缺少线路、号码、坐席、队列和转人工运行状态管理。
6. 缺少系统集成、连接状态、失败重试和 API 核验页面。
7. 多租户与角色切换目前主要是界面演示，缺少对应管理页面。
8. 很多交互使用静态 Mock 或提示消息，不应标记为真实 API、真实通话或已完成 POC。

综合判断：

- 对“业务原型演示”而言：差距中等，核心故事已具备，重点补 4 个业务工作台页面即可明显提升完整度。
- 对“完整 MVP 平台”而言：差距较大，需要补齐业务工作台的关键页面，以及少量系统管理页面；不需要另做一套独立后台。
- 对“生产系统”而言：差距很大，除前端页面外，还必须完成 SmartCall 编译启动、接口核验、真实合法线路、录音、ASR/TTS、打断、转人工、并发、重拨、权限和审计 POC。

| 现有页面 | 当前覆盖 | 主要缺口 | 处理建议 |
|---|---|---|---|
| 运营驾驶舱 | 指标、任务概况、漏斗和经营态势 | 数据来源、成本告警、连接异常、指标下钻 | 保留并增强下钻入口 |
| AI 通话实时沙盒 | 对话、意图、情绪、字段提取、转人工演示 | 不是正式通话记录，也不是实时任务监控 | 保留为演示工具，增加“模拟”标识 |

| 规则与引擎配置 | Prompt、音色、打断、频控、黑名单和企微路由 | 不能表达完整机器人、流程、知识库、版本发布 | 拆出独立的机器人流程页和知识库绑定页 |
| 潜客 360 抽屉 | 画像、匹配、通话质检和生命周期 | 通话全量时间线、授权证据、人工修正记录 | 作为跨页面详情抽屉继续复用 |

## 三、产品结构与缺失页面优先级

### 先确定产品结构

不要把所有能力都放进一个“大后台”，也不要为了补齐功能另做一套独立后台。继续使用同一个前端项目和同一套登录体系，按使用频率拆成两个区域：

- **业务工作台**：给运营、外呼运营、红娘和质检人员使用，放置高频业务流程。现有运营驾驶舱、外呼任务、名单池、红娘跟进、质检和 ROI 报表继续属于这一层。
- **系统管理**：给管理员和技术运营使用，放置低频配置和运行保障能力。建议先作为侧栏中的一个折叠菜单或一个“系统运营”入口，不需要在本轮把所有管理页面做完。

本轮生成的重点是补齐业务工作台的关键断点，再用少量系统管理页面支撑演示。用户、角色、租户、审计、告警等平台化能力暂不作为首批页面。

### P0：必须优先补齐的业务工作台页面

1. **名单导入与合规准入中心**
   - 解决导入、字段映射、格式校验、去重、来源授权、审核、黑名单和退订的完整链路。
   - 可作为现有“名单准入与池子”的一级标签页，不一定增加侧栏一级菜单。

2. **实时外呼任务监控**
   - 解决总名单、待拨、拨打中、接通、有效对话、高意向、转人工、失败、退订、并发、异常、成本等实时态势。
   - 应从外呼任务列表的“监控”按钮进入独立页面。

3. **通话记录中心与单通详情**
   - 解决全量通话台账、录音、转写、摘要、意向评分、结构化字段、命中规则、流程轨迹和转人工记录。
   - AI 通话沙盒保留为模拟工具，不能替代通话记录中心。

4. **机器人与话术流程编排**
   - 解决开场、播报、条件、意图、情绪、字段提取、知识库、服务调用、短信、转人工、挂断和子流程配置。
   - 当前规则页只配置参数，不能替代流程编排。

5. **合规中心**
   - 统一展示授权证据、黑名单、退订、时段、频次、违规记录和审计状态。
   - 演示版可先做台账和规则预览，不宣称真实运营商风控已接入。

### P1：完整 MVP 应补齐

6. **知识库与智能体绑定管理**
   - 管理 MaxKB 应用绑定、API 连接状态、使用中的机器人、测试问答和发布版本。

7. **线路、号码池与 SIP 网关管理**
   - 管理线路状态、主叫号码、并发上限、路由、供应商、健康检查和故障告警。

8. **坐席、队列与转人工监控**
   - 管理坐席在线状态、技能组、队列、等待时长、转接结果和摘要传递状态。

9. **系统集成与连接状态**
   - 管理 SmartCall、MaxKB、CRM/ERP、企业微信、短信、ASR/TTS 和对象存储连接。
   - 展示连接状态、最近核验、失败原因、重试和同步日志。

10. **评分规则与版本管理**
    - 将意向评分、分组阈值、人工修正、规则版本、发布时间和回滚记录独立管理。

### P2：平台化阶段再补

11. **用户、角色、组织、租户和数据权限**
12. **操作日志、系统告警和服务监控**
13. **短信模板与发送记录**
14. **模型效果对比与 A/B 实验**
15. **报表订阅、导出任务和对账中心**

## 四、SmartCall 支撑边界

源码中可以证实存在以下技术结构：

- 外呼任务、任务号码和通话数据模型。
- 通话详情、转接信息、Asterisk CDR、录音路径相关数据结构。
- Answer、Say、Condition、Child、Extract、Intention、Sentiment、Script、Service、Sms、MaxKB、Transfer、Hangup 等流程节点实现。
- ASR/TTS 多供应商适配结构。
- MaxKB 智能体选择、Token 和消息调用结构。
- 线路、坐席、队列相关实体或 VO。
- OAuth2、用户、角色、组织、菜单、数据权限和租户等后台能力。

但下列能力目前只能标记为“未验证”或“待 POC”：

- 完整可用的外呼任务管理 API 和运营前端。
- 真实拨号、接通、录音、下载、删除和权限控制。
- 实时 ASR/TTS 延迟、用户打断和多轮对话稳定性。
- 并发控制、暂停恢复、失败重拨、幂等和宕机恢复。
- 转人工时摘要和客户信息能否可靠传递。
- 名单来源授权、黑名单、退订、频控和投诉处理闭环。
- CRM/ERP 回写、失败重试和对账。
- AI 评分、质检、成本和报表的真实数据链路。

## 五、交给其他 AI 的总体实现提示词

以下内容可直接作为主提示词使用：

```text
你是一名资深企业 SaaS 产品设计师和前端工程师。请在现有项目 smartcall-pro 中继续补齐“知缘 AI 红娘智能外呼运营平台”原型，不要另起一个风格不一致的新项目。

一、项目定位
这是面向婚恋机构运营总监、外呼运营、红娘、质检和系统管理员的智能外呼业务原型。目标是完整表达：
潜客名单导入 → 来源/授权审核 → 创建外呼任务 → AI 首次沟通 → 意向判定 → 高意向转真人红娘 → 红娘跟进 → 报表和质检。

这是业务演示原型，不是真实生产系统。所有静态数据、模拟通话、模拟评分、模拟连接状态必须明确标注“模拟数据”“演示环境”或“待 POC”，禁止把 README 描述、静态 Mock 或数据模型写成“已接入”“已验证”“生产可用”。

二、技术约束
1. 延续当前纯 HTML、CSS、JavaScript 架构，不引入 React、Vue、构建工具或外部 npm 包。
2. 延续现有目录：assets/css、assets/js、assets/js/views。
3. 每个新页面采用 window.XxxView = { render() { ... } } 的视图对象模式。
4. 使用 App.navigate(route) 完成页面切换，在 app.js 的路由 switch 和导航数组中注册页面。
5. 数据统一放在 mock-data.js 或清晰命名的新 Mock 对象中，避免将大量业务数据硬编码在 render() 内。
6. 复用已有 CSS Token、按钮、表格、徽标、抽屉、弹窗、Toast 和 Lucide 图标。
7. 不使用手绘 SVG 图标；优先使用 Lucide 图标。
8. 保证 1440px 桌面端信息密度，同时兼容 390px 窄屏；禁止页面级横向溢出和文字遮挡。
9. 卡片圆角不超过 8px，不做营销落地页，不使用装饰性渐变球或大面积无意义插画。
10. 所有按钮都要有可演示的反馈：切换状态、打开抽屉/弹窗、更新 Mock 数据或显示明确 Toast，不能出现完全无反应的按钮。

三、视觉与体验要求
1. 延续当前克制、专业、数据密集的企业运营后台风格。
2. 继续使用现有品牌色、灰阶、字体、间距、表格和状态标签体系。
3. 页面顶部采用“标题 + 简短说明 + 主操作”的紧凑结构，不增加大型 Hero。
4. 高频操作放在首屏；复杂详情使用抽屉；高风险操作需要二次确认。
5. 状态颜色语义统一：成功/可外呼为绿色，处理中为蓝色，待审核为橙色，风险/失败为红色，停用/未知为灰色。
6. 每个页面必须提供加载、空数据、错误、无权限和正常状态中的至少三种可切换演示状态。
7. 关键数字支持点击下钻；筛选条件变化后更新列表数量和结果摘要。

四、全局导航建议
保留业务工作台一级导航：运营驾驶舱、外呼任务调度、名单准入与池子、红娘跟进工作台、智能质检中心、全链路转化 ROI。
新增业务工作台一级导航：通话记录中心。
新增一个可折叠的“系统运营”分组，不要把它设计成独立网站或另一套后台。系统运营首批只放：机器人流程、合规台账；后续按需加入知识库、线路与号码、坐席与队列、系统集成。
将“AI 通话实时沙盒”放入机器人流程下或保留并标记为“模拟实验室”。
将“规则与引擎配置”保留在系统运营分组中，并与机器人流程、知识库、评分规则建立清晰入口。
暂不新增用户、角色、租户、审计日志、告警等平台化页面到首批原型；这些页面属于后续管理能力。

五、优先实现顺序
第一批只补业务工作台的 4 个核心页面：名单导入与合规准入、实时外呼任务监控、通话记录中心与单通详情、机器人与话术流程编排。
第二批补少量支撑页面：合规中心、知识库与智能体绑定、线路与号码池、坐席队列与转人工、系统集成；这些页面统一放在“系统运营”分组下，不单独创建后台项目。
第三批再考虑平台化管理：评分版本、用户权限、操作日志、告警和 A/B 实验。若只是客户演示，第三批全部可以暂缓。

请按下面的单页提示词逐页实现。每完成一页，都必须检查导航、桌面端、390px 窄屏、空状态、错误状态、按钮反馈和 Lucide 图标渲染。
```

## 六、第一批页面提示词

### 1. 名单导入与合规准入中心

```text
请在现有 smartcall-pro 中实现“名单导入与合规准入中心”，作为现有“名单准入与池子”的标签页或二级页面，并保留现有潜客列表。

页面目标：让运营人员在外呼前完成文件导入、字段映射、格式校验、手机号去重、来源授权审核、黑名单/退订过滤和准入确认。

页面结构：
1. 顶部步骤条：上传名单 → 字段映射 → 数据校验 → 授权审核 → 导入完成。
2. 导入区：文件名、来源渠道、来源说明、联系人授权类型、授权日期、证明附件、责任人。
3. 字段映射表：原始字段、系统字段、示例值、必填状态、映射选择器。
4. 校验摘要：总数、有效、重复、格式错误、黑名单、已退订、待核验、预计可外呼。
5. 失败明细表：行号、脱敏手机号、错误类型、错误说明、处理建议，支持只看错误和模拟导出。
6. 授权审核区：授权状态、证明材料、审核人、审核意见、通过/驳回。
7. 完成结果：生成潜客分组、可外呼数量、被拦截数量、进入任务创建按钮。

必须展示的状态：草稿、校验中、待授权审核、部分通过、全部通过、导入失败。

关键交互：
- 切换步骤并保留表单数据。
- 修改字段映射后重新计算校验摘要。
- 点击错误类型筛选失败明细。
- 审核通过后，“可外呼”数量更新。
- 点击“创建外呼任务”跳转到 campaigns 页面并带入名单分组。
- 所有手机号必须脱敏。

Mock 数据口径：导入 100 条，待审核 20 条，审核通过 80 条，其中退订 2 条、黑名单 3 条、重复 5 条、格式错误 2 条，最终可外呼 68 条。

验收：步骤完整、摘要数字联动、审核有二次确认、失败明细可筛选、390px 无页面级溢出，并明确标记数据为模拟。
```

### 2. 实时外呼任务监控

```text
请实现“实时外呼任务监控”独立页面，从外呼任务列表的“监控”按钮进入，路由建议 campaign-monitor。

页面目标：让运营人员查看单个任务实时进度、并发、接通、意向、转人工、异常和成本，并能执行暂停、恢复和终止演示操作。

页面结构：
1. 顶部任务摘要：任务名、任务编号、状态、执行时间、机器人、线路、名单分组、负责人。
2. 核心指标：总名单、待拨、拨打中、已接通、有效对话、高意向、转人工、失败、退订。
3. 实时漏斗或阶段条：待拨 → 呼叫中 → 已接通 → 有效对话 → 高意向 → 红娘接收。
4. 运行状态：当前并发/上限、线路健康度、平均等待、ASR/TTS 状态、估算分钟数、估算成本。
5. 实时呼叫列表：脱敏号码、潜客、当前状态、已用时、当前流程节点、意向变化、坐席/队列、操作。
6. 异常面板：线路拥塞、识别超时、转人工排队、重拨等待、退订请求。
7. 事件日志：时间、事件、对象、结果、来源，支持筛选。

关键交互：
- 模拟实时刷新，但提供“暂停刷新”控制。
- 暂停/恢复/终止任务必须二次确认并更新状态。
- 点击指标筛选实时呼叫列表。
```

## 八、系统运营后台完整提示词

下面这段提示词用于后续一次性生成系统运营区。它和业务工作台属于同一个前端项目，但必须通过导航分组、页面职责和角色权限保持边界清晰。

### 系统运营区总提示词

```text
请在现有 smartcall-pro 原型中一次性补齐“系统运营”分组，不要新建独立后台项目，不要把系统配置内容塞进业务工作台页面，也不要重写已有业务页面的视觉风格。

一、系统运营区定位
系统运营区面向系统管理员、技术运营和主管管理员，负责低频配置、运行保障和合规管理。它不是运营人员每天处理潜客和任务的工作台。业务工作台继续保留运营驾驶舱、外呼任务、名单池、通话记录、红娘跟进、质检和 ROI 报表。

二、导航结构
在现有侧栏中增加一个可折叠的“系统运营”分组，包含：
1. 机器人流程
2. 合规中心
3. 知识库与智能体
4. 线路与号码池
5. 坐席与转人工队列
6. 系统集成
7. 评分规则版本
8. 操作审计日志

系统运营区页面不得出现在业务工作台的高频导航中。移动端允许将该分组收起为“系统运营”入口，但页面路由必须保持可访问。

三、统一页面框架
每个系统运营页面都使用统一的企业后台框架：页面标题、用途说明、状态摘要、筛选工具栏、主数据表、详情抽屉或编辑面板、操作反馈。不要使用营销式 Hero、大面积插画、装饰性渐变或堆叠卡片。

所有配置页面必须支持：正常状态、空状态、加载状态、错误状态、无权限状态；保存前显示未保存状态；离开未保存页面时弹出确认；高风险操作二次确认；保存、启停、测试、发布、回滚、重试操作都必须有 Toast 或状态反馈。

四、角色和菜单可见性
使用 Mock 角色模拟菜单权限：
- 运营人员：只看业务工作台，不能进入系统运营。
- 质检人员：可看通话记录、质检和合规中心，只读系统配置。
- 技术运营：可看机器人流程、知识库、线路、坐席和系统集成。
- 管理员：可看全部系统运营页面，包括审计日志和评分规则。

权限不足时显示“暂无访问权限”状态，不要直接隐藏所有入口导致无法演示权限逻辑。页面中的敏感配置必须脱敏，不展示明文 Token、密码、密钥或完整服务器地址。

五、跨页面联动
- 发布机器人流程后，外呼任务创建页可选择该流程。
- 停用线路后，任务创建页不能选择该线路，并显示停用原因。
- 知识库绑定机器人后，流程节点属性中显示已绑定知识库。
- 合规中心加入黑名单或退订后，名单池和任务创建页同步拦截该潜客。
- 坐席离线后，转人工队列显示可用坐席减少。
- 评分规则发布后，通话详情和质检页面显示对应规则版本。
- 操作审计日志记录发布、停用、删除、导入、审核、连接测试和权限变更等关键操作。

六、技术约束
延续纯 HTML、CSS、JavaScript 和现有 smartcall-pro 目录结构，不引入 React、Vue、构建工具或新的 npm 包。每页使用 window.XxxView = { render() { ... } }，通过 App.navigate(route) 注册路由，复用现有 CSS Token、表格、抽屉、弹窗、Toast 和 Lucide 图标。统一使用 MockData 或 localStorage 保存演示状态。

七、真实性边界
系统运营区只展示“原型配置”“模拟状态”“待接口核验”。不要把 SmartCall 的 Java 模型、SQL 表、README 或流程节点写成已经完成的生产接口。连接测试、线路健康、坐席在线、知识库调用、发布和审计均为演示 Mock，必须在页面上明确标注。
```

## 十二、推荐实施节奏

这份提示词的目标是让其他 AI 在现有原型上做“增量补齐”，不是一次生成一套完整后台，也不是重写整个产品。

1. 第一轮只生成“名单导入与合规准入中心”。
2. 第二轮生成“实时外呼任务监控”。
3. 第三轮生成“通话记录中心与单通详情”。
4. 第四轮生成“机器人与话术流程编排”，并把 AI 通话沙盒归入模拟实验室。
5. 第五轮统一修正业务工作台导航、Mock 数据和跨页面联动。
6. 第六轮按需要生成“系统运营”分组中的合规、知识库、线路、坐席和集成页面。
7. 最后一轮只做响应式、状态覆盖、文案边界和控制台错误检查。

不要在一次提示中要求 AI 同时重写所有现有页面，也不要为了展示管理能力创建独立后台项目。优先完成 P0 业务工作台页面并走通主演示路径，再按实际需要补系统运营页面。
